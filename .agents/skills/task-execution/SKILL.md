# Execute one authorized Genesis task

Use for an explicit implementation request such as “Görevimi başlat” or “Bu görev sözleşmesini uygula.” Discussion and preparation alone grant no edit authority. Run the following sequence once for the named task.

1. **PREFLIGHT.** Use [repo-bootstrap](../repo-bootstrap/SKILL.md). Pin live canonical main, confirm the approved working branch and base revision, and record starting changes with provenance. Stop on conflicts or unknown work. Use the currently effective policy identified through [AGENTS.md](../../../AGENTS.md).
2. **AUTHORIZATION.** Confirm the explicit human instruction and any separate protected scope authorization against the applicable policy. For products, use the pinned task registry, accepted records and live prerequisite evidence. For a migration, use its separately authorized bounded contract and verify its predecessors. MIG-03 consumes no product turn. A local v3 proposal grants no hosted authority. Stop on any missing or contradictory authorization. The local helper below checks the recorded contract against Git and policy data. The human evidence must be established independently of the JSON input.
3. **CONTEXT_RECOVERY.** Use [task-context](../task-context/SKILL.md) to recover mandatory sources, scope, acceptance criteria and relevant tests with source revisions. Use the task registry and evidence for accepted work. Read the historical ledger and addendum as historical context. Consult verified lock records where available. Block changes requiring unavailable lock evidence. Keep assigned owner, actual implementer, PR author, commit authors, reviewer and human approver separate.
4. **SCOPE_VALIDATION.** Confirm the contract bounds before edits and save a successful `start` record. The helper preserves the initial index and named existing changes, checks protected paths and rechecks scope at review. Keep checks, generated output and review evidence outside the checkout unless the task explicitly authorizes those files.
5. **IMPLEMENTATION.** Once authorized, enter `IMPLEMENTATION_IN_PROGRESS`. Inspect the existing implementation and use the smallest change that meets the contract. Preserve interfaces, frozen inputs and unrelated work. Add applicable tests and documentation. Stop on scope expansion. Follow the bounded repair policy in [verification](../verification/SKILL.md).
6. **LOCAL_VERIFICATION and DIFF_REVIEW.** Discover actual commands through [verification](../verification/SKILL.md). Use `review` for the mechanical checks and independently inspect the diff and any task-relevant ignored content. Record actual commands, environment, exits, results, evidence and source revisions. A failed, missing or blocked mandatory check prevents `LOCAL_VERIFIED`. Record pre-existing pilot failures separately and block any check that depends on the affected inputs. Hosted verification requires hosted evidence.
7. **REPORT_GENERATION.** Use the report and review guidance in [development-handoff](../development-handoff/SKILL.md), without restarting its workflow. Include task, developer and implementer, source SHA, branch, diff and changed files, acceptance criteria, verification and failures, security findings, protected-file results, limitations, approval and publication status. Respect the existing report's owner and scope. Finalize the in-scope report before capturing the final review ID. A report edit after capture requires a fresh review.
8. **HUMAN_REVIEW and STOP.** Present the exact reviewed diff and review ID to the authorized developer. A successful review records `LOCAL_VERIFIED`, `REVIEW_REQUIRED` and `HUMAN_APPROVAL_PENDING`. Ask for one explicit choice. For **ONAYLA**, verify identity and the review ID referenced by the human. For **DÜZELT**, make only authorized changes, rerun affected checks and request fresh approval. For **REDDET**, preserve the work and stop. Any changed content or source invalidates the earlier review. Even an approved result is evidence for a separate publication process. Stop here.

## Local helper contract

[task_execution.py](../../../scripts/governance/task_execution.py) uses Python 3.11 or later and existing Git and governance tools. Store the contract, session and review JSON in a private directory outside the checkout. Use a trusted Git executable on PATH and review every command argument from actual test sources before running it. Do not place credentials in the contract or commands. The helper runs approved checks once with a bounded timeout and reports their exit codes without retaining output. Inspect evidence separately for tests that exit zero while skipping mandatory cases. Such a result still blocks human review readiness.

Required JSON fields are `repository` (owner/name), `task_id`, `task_title`, `task_type` (`product` or the supported `migration`), `authorized_developer`, `branch`, `base_revision` (working HEAD), `source_main_sha`, `objective`, `authorization_reference`, `prerequisites`, `required_context`, `allowed_paths`, `protected_paths`, `acceptance_criteria`, `verification_requirements` and `stop_conditions`. List prerequisite Plan IDs and mandatory pinned source paths. Scope entries are exact paths or directory prefixes ending in slash. `protected_paths` adds exclusions. `existing_changes` may enumerate exact starting staged, unstaged or untracked paths after their provenance is verified. Those paths remain unchanged during execution.

`verification_requirements` maps check IDs to argument arrays or null when unavailable. The helper adds mandatory checks from the task and changed paths. Product prerequisite validation uses the existing read-only GitHub client with `GH_TOKEN` available to that process. `protected_authorization`, when applicable, must record `reference`, `repository`, `task_id`, `authorized_developer`, `branch`, `base_revision` and exact `paths` from independently verified owner evidence. The immutable pilot and canonical registries are excluded from helper-authorized edits. The migration mode is limited to MIG-03 paths and separate owner evidence.

Run from the checkout root. Replace file arguments with the actual private paths. Save the JSON stdout from `start` as the session record and from `review` as the review record. A blocked review may still emit JSON and exits nonzero.

```text
python -B scripts/governance/task_execution.py start --contract CONTRACT.json
python -B scripts/governance/task_execution.py review --contract CONTRACT.json --session SESSION.json
python -B scripts/governance/task_execution.py decision --contract CONTRACT.json --session SESSION.json --review REVIEW.json --review-id EXACT_REVIEW_ID --choice ONAYLA --developer LOGIN --approval-ref EXACT_HUMAN_DECISION_REFERENCE
```

Use `decision` only after receiving the actual human decision on that exact review. It writes one receipt per review alongside the private session file. It cannot authenticate an off-platform message or defend against deliberate editing of local records. Supply the review ID in the human approval evidence and carry the approved contract, snapshot ID, results, reviewer and approval reference to any future MIG-04 process. MIG-04 must revalidate identity, source and content against that evidence. MIG-03 records no publication authorization, task acceptance, event-log update, phase lock or rotation and produces no next task.
